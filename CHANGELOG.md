## v0.6.53 — 2026-08-15 — account plan quota: the numbers were already on the wire

From Bogdan: *"see if the responses contain the session/weekly remaining token percentage — maybe we have it and we're just not surfacing it."* We did, and we were. The API reports account plan consumption on the response **headers** of every successful turn (`anthropic-ratelimit-unified-*`) — never in the SSE body — and `receipts.py` has been capturing them verbatim into `.response.json` since the beginning. A `grep -rn ratelimit` over the whole repo returned exactly one hit, and it was a comment. New module `proxylab/quota.py` reads them; no capture change, so the corpus is backfillable.

- **Surfaced in four places, all account-scoped.** `/_status` gains a **top-level `quota`** block (NOT per-session: every agent on the box spends the same plan, so a per-session copy would imply a per-agent fact that does not exist); `turn.completed` gains a compact `data.quota` so a live consumer updates without polling; `/_admin` renders a "plan quota used" line; `/_identity` gains `capabilities.quota`. Parsed once in `receipts.anthropic()` — the single turn-finalize convergence — never in a streaming closure. Consumer contract: INTEGRATION.md § Plan quota.
- **`utilization` is the fraction CONSUMED, not remaining.** Both directions ship pre-computed (`used_pct`/`remaining_pct`) so no renderer has to get the inversion right: at 0.93 the two readings differ by more than 10×, i.e. the error is largest exactly where the number matters.
- **A 429 CARRIES NO QUOTA HEADERS AT ALL** — measured 102/102 in a 4k-capture window; the body is `{"type":"rate_limit_error"}` with no utilization on it. So the one response that proves you hit the wall cannot raise the percentage. The last good reading is kept and the rejection recorded beside it as `last_429`, because a bar that freezes at the moment it matters reads as a stuck value, not as a limit.
- **`status` escalates at the threshold the server publishes on the same response** — measured over **98,456 captures** carrying these headers: across 22,312 readings with a `surpassed-threshold`, `utilization >= threshold` ⇔ `status != "allowed"` with **zero counter-examples in either direction**. Every published threshold so far is `0.75` (`1.0` on the 290 `rejected` rows). Both facts matter: it is the server's lever *and* currently a fixed number, so render the sentence from the payload rather than hardcoding 75. Per-window: `7d` warns 0.75–0.99, `7d_oi` 0.75–0.95, and **`5h` has never warned once** (max observed 0.83).
- **Windows are DISCOVERED from header names, not hardcoded.** A `7d_oi` meter appeared in 256 of 4,000 sampled captures with no announcement; anything unrecognized lands in `unmapped` rather than being dropped, so a new meter is visible the day it ships instead of the day someone re-greps the corpus.
- **THE BUG THE MEASUREMENT CAUGHT, and the reason to measure rather than reason:** the claim→window map first contained `seven_day_oi`, **inferred by analogy** with the `7d_oi-*` header prefix. The wire never sends that string — it sends `seven_day_overage_included` (n=1,052), alongside `five_hour` (76,784) and `seven_day` (20,620). The header prefix and the claim word are **different vocabularies**, and deriving one from the other silently nulled `primary` on ~1% of turns — a defect that presents as intermittent flakiness, not as a wrong value. `test_quota.py` now pins all three observed strings. (clodex reports it would have inferred the identical wrong string by the identical reasoning.)
- **Freshness is part of the reading.** Nothing polls; these numbers move only when a turn is forwarded, so every snapshot carries `as_of`/`age_s`. Persisted owner-scoped in `warmth.sqlite` and restored at boot — after a restart a stale-but-stamped reading beats a blank one, because `age_s` makes the staleness legible.
- New `test_quota.py` (37 checks, incl. real captured headers). Kill switch `QUOTA_TRACK=0`.

## v0.6.52 — 2026-08-12 — the two causes of an API call: operator-initiated vs model-initiated

Follow-on to v0.6.51, from Bogdan reading the new labels: *"the model emitting tool_use and the tool_result aren't exactly the same round trip"*. Correct — and the label was flattening two different facts into one. Renderer-only change (`views.py`); no transform, capture or wire behaviour touched.

- **An assistant block was dated by the call that RE-CARRIED it, not the response that PRODUCED it.** Every block first appears on the wire in some request, which is what the debut map measures — but an assistant message was emitted as the *response to the previous call* and merely ships back as input on this one. **Wire-proven on a live capture: request 058's response emitted two `Bash` tool_use at 12:29:13; request 059 carries that identical assistant message at `messages[6]` at 12:29:30.** Labelling it `call 3` dated it 17s late and credited the wrong round trip. Assistant blocks now read **`reply k-1`**; `tool_result` blocks keep `call k`, because they were written by the CLI locally, cost no API call of their own, and first reach the wire exactly there. On call 1 there is no `k-1` to name (a resumed or swept session), so the label falls back to the carriage form with a tooltip that says which fact it is stating — rather than inventing a `reply 0`.
- **The API has one request shape but TWO causes, and the page can now tell them apart.** A call whose trigger is a real user turn is **operator-initiated**; a call whose trigger is only `tool_result` blocks is **model-initiated** — the model's own previous response demanded it by emitting `tool_use`, nobody asked, and the CLI is closing a loop the model opened. Both re-carry the entire window at full price. Marked `●` and `↻` on the triggering block only (stamping every block would repeat the fact once per tool_result in a fan-out message).
- **Fan-out is the number this exposes, and nothing before could state it.** New header stat: **`fan-out ×N`** = calls per operator-initiated call. **Measured across the live corpus (1,043 sessions, 14,364 calls): 19.9% operator-initiated, 78.0% model-initiated, ×5.03 overall**, with individual sessions reaching **×88** — one thing asked, 88 billed round trips, 87 of them the agent's own choice to go look at one more file. That is the carriage thesis stated per-decision instead of per-session.
- **Free — no new I/O.** Derived from the existing debut map plus the payload the renderer has already parsed. Within a live lineage every call's debut messages are still present by construction (that is what monotonic growth means).
- **Validated against independent evidence, not just itself:** the prior call's response SSE must contain `tool_use` iff the next call is model-initiated — a different file, different signal. **5,227 call-pairs checked across 400 sessions: 99.92% agreement, and all 4 residuals traced to the harness (call→file alignment), not the classifier.** Two traps found while validating, both in the *checking* code: an SSE grep for `"type":"tool_use"` misses padded JSON (the wire pads inside the object), and a diagnostic that forgets `core.LOG_DIR` gets an empty map and reports a vacuous pass. Also `n_op` is deliberately **not** reconciled against `n_turns` — that counts prompts in the window, this counts calls opened within the captured lineage; making one derive from the other would let a real disagreement pass as a render bug.
- **A call that debuted no user message (a retry) is left unclassified rather than guessed at** — operator + model can legitimately total less than the call count, and the header tooltip says so. **2.1% of live calls land here.**
- `test_call_ordinals.py` +7 cases (46 checks). All three new guards **mutation-tested**: dating assistant blocks by carriage fails 4 checks, letting any role trigger a call fails 4, accepting mixed content as tool_result-only fails 1. *(A stale-`.pyc` trap surfaced doing this: CPython validates bytecode on source **mtime-seconds + size**, so a same-length edit restored within the same second is silently ignored — a "restored" run kept executing the mutant. `find . -name __pycache__ -delete` between mutations.)*

## v0.6.51 — 2026-08-12 — /_session block labels answer "when did this happen"

- **The `#N` on every `/_session` block was the message's INDEX in the payload array, which reads like a round-trip counter and is not one.** Found from the page itself: a request carrying a dm *and* the SessionStart system message that arrived with it rendered as `#0` and `#1` — two API calls on screen, one on the wire (confirmed on a live capture: the request before it carries `n_messages: 1`, the next carries `n_messages: 2` with both blocks present). An index answers "where in the array", never "when did this happen", and the latter is the only question this page is read for.
  - Blocks now read **`call 3 ×16`** — which call FIRST carried the message, and how many calls have re-sent it since. The multiplier is the carriage fact this proxy exists to price: a block debuting on call 2 of an 18-call session has been paid for on 17 round trips. The header bar gains an **API calls** count next to `turns`, deliberately a separate number: a turn is one operator prompt, a call is one billed round trip, and one turn is many calls (every tool step is its own).
  - **No new capture data and no body parsing.** Every request already records `summary.n_messages` (`== len(body["messages"])`, the v0.6.48 invariant), read from the existing 4 KB tail read; within a lineage that count only GROWS, so the series of lengths **is** the debut map — a message at index i first shipped on the earliest call whose count exceeded i. No content is ever compared.
  - **Cost is bounded by the LINEAGE, not the session.** The walk runs newest-first and stops once the live lineage is covered: **7 ms** on a 20-request session, **75 ms** on a 9,901-request one — the big session is cheap precisely *because* a compact left ~50 live calls. A forward full-directory scan of that same session costs **7.5s**, which is the expensive scanning this avoids.
  - Excludes two populations that would otherwise shift every ordinal after them: **subagent lines** (they share the parent's session_id but carry their own private message array) and **one-message utility side-calls** (the title probe and the WebFetch/WebSearch summarizers — real API calls, but not round trips of *this* conversation). Where nothing can be attributed the label falls back to the bare index, exactly what the page rendered before: a swept capture dir degrades the LABEL, never the page.
  - **THE TRAP, because the first version had it:** the backward walk must break on a **strictly longer** count, not on "stopped decreasing". Retries and payload-neutral turns legitimately repeat a length, and breaking there truncated the map to a single call on **5 of 53 live sessions** (one lost 73 calls) while still looking well-formed — every ordinal it emitted was `1`, which is self-consistent, monotonic and useless. Only a COVERAGE assertion catches that, so `test_call_ordinals.py` leads with it and every case pins counts rather than shape. Same failure mode as the `_turn_clock` bug: an emptied map is trivially monotonic.
  - Validated against an independent forward full scan: **8,582 messages across 126 live sessions, 100% agreement.**

## v0.6.50 — 2026-08-11 — retirements, an ownership guard, and the CLI stall timeout

A cleanup release: three features retired on measurement, one foot-gun closed, and one confound found in the A/B harness itself. **No transform behaviour changes for a session that was not using `/_pot` or `SPLIT_SYSTEM_REST`.** Surface touched: `transforms.py` (−135 lines), `server.py` (two call sites), `restore.py`, plus `run_release.sh`. SC / INJECT / RESP untouched.

- **`run_release.sh` refused to kill a proxy this lab didn't start.** Its first act was `kill` on whatever LISTENS on `$PORT`; under the clodex-managed-vendored model that pid is the live proxy, so the bare script took :7800 and every warm prefix with it. The guard reads ownership from the LISTENER's cwd, not from config, so it stays correct if the deployment model changes again: ours → proceed, no listener → proceed, anything else (**including a cwd it cannot read**) → refuse, fail closed. `RUN_RELEASE_FORCE=1` overrides; `RUN_RELEASE_CHECK_ONLY=1` runs only the guard.
- **`/_pot` (boiling-pot tier 2) retired — the mechanism worked, the hypothesis came back negative.** Live 30-day window: **130 of 7,425 reads redundant (1.75%)**, 94.8% of files zero-redundancy, and 61% of the remainder were scratchpad `.diff`/`.patch` re-reads — **~$2.39 against a $7,488 bill (0.03%)**. Redundant reads are not where the money is (cf. tool-trim −72.7%, strip-thinking 16–22%). `proxylab/pot.py` + `test_pot.py` deleted; **`file_heat` ROWS deliberately kept — retiring a feature is not a reason to drop data.**
- **The rider latch (`_RIDER_LATCH`) retired as vestigial** (~135 lines + its table + restore path); the mid-turn strip + marker gate replaced the `busted_from` gate it widened. **The durable lesson is kept as a comment in `transforms.py`, because it generalizes past the code that taught it:** the original gate fired stubs only inside a region the thinking-strip had already busted, and once a `/_compact` bake made history arrive PRE-THINNED that inverted — RE-APPLYING a transform is what keeps bytes identical to the warm prefix, and SKIPPING it originates the bust (measured: write 117,758 / read 20,301). **Any "only act when something else already busted" condition is unsafe the moment a second path can pre-thin the same history.** Determinism beats conditional cleverness for anything editing a cached prefix.
- **`SPLIT_SYSTEM_REST` retired: a second answer to a problem `RELOCATE_ENV_TO_TAIL` already solves better**, and it had **0 firings in 8,000 sampled captures**.
- **`test_registry.py` (new): both module registries must list every module, asserted as a set.** The package `__init__` is lazy and the `logproxy.py` shim is eager — two hand-maintained lists that a new module can silently fall out of. Set equality against the directory catches it at test time instead of at import time in someone else's process.
- **`ab_run.py` now pins `CLAUDE_STREAM_IDLE_TIMEOUT_MS` — a confound inside the measured quantity, not a nuisance.** The CLI cuts any stream silent for 300s (`API Error: Response stalled mid-stream`) and retries with backoff `[15s,30s,60s,120s]`; **a retried turn re-ships and re-bills its whole prefix**, and `ab_analyze` prices arms from the captured billing blocks — so one arm eating a stall shows up as treatment cost, and the two arms need not have been on the same threshold. Proxied traffic sits on a **FLOOR**: CLI 2.1.227 resolves `max(env, 300000)` clamped `[1, 1800000]`, so the var can only RAISE it. Measured on the dev box: unset → cuts at **304.5 / 304.0 / 302.3s**; set → completions at **675–696s**, the only streams past 600s in 76,949. Checked whether it had already corrupted a conclusion: **longest completed stream in any past A/B arm was 14s** — no prior result affected. Deliberately NOT applied to `hold.py`'s auth bootstrap, which has no reason to need it; a fix applied everywhere it syntactically fits stops being a fix and becomes folklore.
- **`analyze_truncations.py` (new, read-only): mid-stream cut rate + event attribution**, with the denominator traps that bit us encoded in its docstring — population mixing, right-censoring, **ineligibility** (a window where the mechanism could not fire at all, which is not censoring), and a rate that implies exchangeable trials when the events are episodes. `--eligible-from/--eligible-to`, and it **says in its own output** when eligibility defaulted to the event span rather than being stated.
- **Five finished scratch artifacts removed** (`STRIP_AB_RUNBOOK.md`, `STRIP_AB_TASK.md`, `scratch_fyi_watch.py`, `analyze_read_edit.py`, `cv-settings-deny.json`), each verified dead in **both** repos with a working positive control — a grep over this repo alone is not evidence when a vendored consumer reaches internals through a PEP-562 lazy shim. **`analyze_churn.py` and `analyze_truncations.py` were kept and documented in OPERATIONS.md instead: *finished* was the argument for deleting a script, never *orphaned*, and an undocumented reusable tool is invisible.**
- **OPERATIONS.md corrects the vendor flow's ownership:** `vendor-wirescope.sh` lives in the clodex repo, not here — **this repo cannot run it and must not try**, and a GUI restart busts every warm prefix, so scheduling it is the operator's call, not something a release here should imply.

## v0.6.49 — 2026-08-11

- **The bust detector was measuring the wrong thing: it called a big WRITE a bust, when a bust is a LOST READ.** Found from a live report — a reviewer agent on a 5m TTL was flagged with 4 busts; hand-checking the receipts showed it never lost a single cached token (every turn's `cache_read` equalled the prior turn's `read + write`, max idle gap 244s against a 300s TTL). The old rule fired when `write / (read + write + uncached) >= 0.15`.
  - **Why that is wrong in BOTH directions.** A big write does not mean a bust: a window that merely GROWS writes a lot relative to its own size, worst on early/small turns where one tool result is half the window — **1,100 false alarms** across a 61.8k-transition corpus sweep, every one with the prefix fully intact. And a small write does not mean safety: a lapse re-reads a short static floor and writes little relative to the new window, so `write_frac` stays near 0 while the history evaporates — **2,046 real busts missed, the worst losing 138k tokens at `write_frac` 0.00**. The two errors are not symmetric in cost; the misses were the expensive half and were invisible.
  - **The receipt states the answer directly.** `cache_read` IS the length of the prefix the API matched, so a bust is that number SHRINKING. New `report._prefix_loss` + `lost_tokens`/`lost_frac` on every transition; `severity` splits on the share lost; `worst` now ranks by loss instead of by write (a turn that wrote more because the conversation grew is not worse than one that lost more).
  - **Baseline is the prior `cache_read` alone, deliberately not `read + write`.** The tail a turn writes past its last breakpoint is routinely not re-read by the very next request — the CLI's rolling marker sweeps it in a turn later. Charging that as loss would flag normal deferred-write behaviour: **1,127 such turns / 19.3M tokens**, and in 494 of the 536 clearest cases `read_k == read_{k-1}` EXACTLY. Reported as `unread_write` instead — visible, not damage.
  - **One exception, measured not assumed:** when the prior turn matched nothing (cold start, or a just-busted turn), read-only baselining is blind — every later number is >= 0, so a total loss on the next turn scores zero. There the prefix IS the write, so the write is the baseline, gated by `BUST_COLD_BASELINE_MIN_FRAC` 0.25 because it cannot separate the deferred tail as cleanly. The two populations are far apart with an **empty valley between 0.13 and 0.50** (156 of 168 cases lose everything). Recovers **168 busts / 13.8M tokens** the read-only rule missed.
  - **Both engines fixed together**, since a consumer sees them as one product: `report.bust_series` (disk, `/_bust`) and `warmth._classify_bust` (live, `/_status.busts`). The live twin needed the prior receipt, so `session_head` gains `read_tokens`/`write_tokens`; a pre-migration row has no baseline and **DECLINES to judge rather than guessing** (the rule the warmth gates already follow). The loss test replaced the GATE only — all five classes (tools/system/preamble/conversation/compact/lapse) still classify, verified live.
  - Thresholds are stated, not fitted, because the loss distribution is **not** bimodal (p25 0.08, p50 0.44, p75 0.88): the 1024-token floor is the minimum cacheable block (a shrink smaller than one block cannot be a lost block — drops 152 of 3,214 flagged transitions carrying 0.06% of lost tokens), and `full-rewrite` at >=0.9 lost is a reporting convention meaning "essentially nothing survived".
  - Corpus after the fix: **3,224 busts in 62,016 transitions (5.2%)**, 187M tokens lost, led by `conversation` (2,088 / 114M) — that concentration is a separate open question, not addressed here. The reviewer session that started it reports **0**.
  - New `test_bust_loss.py` (35 checks) drives BOTH engines through the same scenarios and pins the constants; mutation-checked 9/10 (the survivor is an equivalent mutant, documented in the suite). `/_session`'s bust panel now leads with what was LOST and names a deferred write as such. Fixture receipts in `test_warmth_store.py` were scaled from toy values (100/200 tokens) to realistic ones — a 100-token prefix is smaller than the minimum cacheable unit and could not express a bust at all.

## v0.6.48 — 2026-08-10

- **`/_bust` was O(session bytes) when the question it answers is O(busts): 16.4s to open the cache-bust popover on a long session.** Profiled by clodex against a live 7,458-turn / 3.0 GB session (`BUST-PERF-PROFILE.md`): `report._iter_pairs` alone was **15.7s** of a 21.6s `bust_series`, serialization 0.02s — it `json.load`s **every** `*.request.json` in the dir, and a request capture holds that turn's whole `messages` array (2.77 GB, mean 0.37 MB each), to answer a question about **100 busts out of 7,125 transitions**.
  - **The fix is to read the bill first.** Bust and severity already come from the RECEIPT (`response.json` billing — "the bill is ground truth for magnitude"); the request BODY is needed only by `_first_divergence`, which runs only on busts. New `report._bust_scan` decides everything from receipts plus two cheap reads, then `_bust_body` parses the ~100 bodies a locus is actually computed for. **Measured 15.4s → 1.5s summary / 4.5s detail end-to-end; on 200 stable sessions (59,704 turns, 1,937 busts) the payload is byte-identical and total time 100.6s → 21.2s (4.8×).**
  - **Two structural facts about the capture format carry it, both verified against the corpus rather than assumed.** (1) `summary.n_messages == len(body["messages"])` — the writer builds both from the same parsed object, so the sidecar substitutes for counting the array (this feeds `prev_messages`/`cur_messages`, which decide the `compact`-vs-`conversation` class). (2) **`summary` is present iff `body` is a dict** — the writer only emits a summary after reading `obj["messages"]`, so an unparseable or non-object body has none; that is what lets the scan reproduce the old code's transition-chain BREAK without opening a body. Checked on **all 124,026 records: 0 violations**, and invariant 1 on a 4,134-request sample across all 1,039 capture dirs.
  - `ts` comes from a **200-byte head read** (it is the 2nd key the writer emits; measured at byte offset 17–20 corpus-wide) and `summary` from a **4 KB tail read** (it is the last key; max observed 991 B). Either miss falls back to a full parse of that one file — a format change costs speed, never correctness.
  - **`transitions` is now behind `?detail=1`**, matching `/_report?detail=1`'s `series`. It was one entry per turn = **5.1 MB of the 5.3 MB payload**, and the only consumer (clodex's bust popover) reads `busts`/`count`/`n_static_prefix_busts` and never touches it. Summary payload **5.3 MB → 0.22 MB**. Every other key is byte-identical between the two modes.
  - **`/_session?...&turn=` had the same defect via a second path** and is the slower one an operator actually hits: `views._main_line_turns` called `_iter_pairs` to get `{stem, seq, ts}` — three fields it reads off the filename and a header — and paid a full-corpus body parse for them. Moved onto the same scan: **30.0s → 3.9s, byte-identical HTML.** (Not in the original profile; found while verifying the endpoint fix.)
  - **A trailing-window scan was considered and rejected** (the operator's first instinct): the chip counts busts for the whole session and the age triad reports the FIRST one, so a window silently drops older busts and reports a first-bust date that is just the window edge. Captures are immutable once written, so per-stem memoization would get the same speedup with no semantic drift — worth doing *after* this, not instead of it.
  - `test_bust_scan.py` (new, 37 checks) pins both invariants, the ordering key, the chain break, the fallback path and the `detail` split, with an end-to-end case that runs a body-parsing reference implementation against the fast path on the same fixture. Mutation-proven: **9 of 10 seeded faults killed**; the survivor is an unreachable `isinstance` guard, left as cheap defence and documented as unasserted rather than papered over. 12/12 suites green.

## v0.6.47 — 2026-08-03

- **`/_session`'s cache-breakpoint and turn-header token figures were ~33% under the truth, and disagreed with the receipt shown at the top of the same page.** Reported against a live session whose header read a real `context = 90.1k tok` while its last cache breakpoint claimed `prefix above ≈58.7k` — implying ~40k of uncached tail on a turn whose `input_tokens` was **2**. Two different instruments: the header is the wire receipt, the breakpoints were a flat `chars // 4` anchored to nothing. New `proxylab/tokest.py`; render-only, no wire path touched.
  - **The fix rests on a fact the wire hands us free, per request: `cache_read + cache_creation` is the EXACT token count of the prefix through the last cache marker.** Validated against `/v1/messages/count_tokens` on 10 sessions — holds to a constant **+41…+45 tok** of framing (0.04–0.24%), i.e. an additive offset, not a scale error. So every captured request carries one exactly-known point on its own cumulative-token curve; the estimate's level is fitted to that point, which is why the page now agrees with its own header **by construction** rather than by luck. The final breakpoint renders as `measured`, without the `≈`.
  - **Four things the flat `/4` got wrong, each measured rather than guessed.** Per-segment density (tool schemas **2.71**, system prose **3.11**, message JSON **2.98** ch/tok); a **219-tok** fixed tool-use preamble present in no captured character; **7 tok** of request framing; and **images, which tokenize by PIXEL AREA, not characters** — one captured 2000×552 PNG was 294,696 base64 chars for **1,443 tokens** (204 ch/tok against ~2.6 for text), and drove the 188% worst case single-handed. Images are now priced `w*h/750`, excluded from the char count, and held OUT of the calibration ratio since they are already exact.
  - Accuracy vs `count_tokens`, on **25 clean held-out sessions / 81 breakpoints** (excluding both the constant-fitting set and the constant-*measurement* set): median **33.0% → 2.3%**, p90 36.3% → 13.2%, max **66.6% → 19.5%**. Improved on **81/81**.
  - **`Σ` on the turn headers had a second, independent bug**: `_turn_weights` was called with `messages` only, so the running total omitted the tools+system preamble entirely — ~17k tok on the reported session, compounding with the `/4` bias to read ~40% under the header. It now reads off the calibrated curve and converges on the receipt at the final turn.
  - **`SYSTEM_CHARS_PER_TOK` was itself wrong at first (3.38), and the method that found it is the transferable part.** It had been grid-fitted against whole-request anchors — which are message-dominated, so system prose barely constrained the fit — and the resulting 8% error landed *entirely* on the tools/system breakpoints, the ones carrying no message content for the calibration to absorb it. Re-measured by **differencing** (`count(tools+system) − count(tools)`) over 12 sessions: **3.11**. Differencing isolates a segment; prefer it over fitting for any future re-measurement.
  - **Two alternatives tried and REJECTED, recorded in the module so they aren't re-attempted.** (1) A second free anchor from `cache_read` alone — it is a prefix cached by an *earlier* request at an index we don't hold (measured 99,872 against second-to-last-marker truth of 48,666); it anchors nothing placeable. (2) Applying the correction to the messages segment only: better in-sample *and* better on held-out median (0.9% vs 3.1%), and **wrong** — split by breakpoint type it was a coin flip where the head dominates (19/40) and clearly worse wherever messages exist (max 17.7% vs 3.3%, winning 2/26). Its median advantage came from head-only breakpoints being the majority of the sample, not from the model being better. **An aggregate hid two populations moving in opposite directions**; the same comparison at n=8 and n=74 gave opposite verdicts, and neither was the answer.
  - Codex/openai keeps flat `/4` via an explicit `cpt=4.0` at the call site: different tokenizer, and its server-side caching yields no receipt to anchor against, so the Anthropic-calibrated constants would be unjustified there. Marked rather than silently inherited.
  - `test_tokest.py` (new, 54 checks) pins it against `count_tokens` values measured on real captures — not self-generated.
